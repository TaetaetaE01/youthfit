# 첨부 임베딩 LLM 선별 게이트

- 날짜: 2026-06-06
- 상태: 설계(브레인스토밍 산출물)
- 관련 모듈: 백엔드 `rag` (RAG 인덱싱), `policy`(첨부), `metrics`(LLM 비용)
- 적용 범위: **전 소스**(온통청년·복지로·몽땅청년 등 모든 정책)

## 배경 / 문제

`RagIndexingService.indexPolicyDocument` 는 정책의 본문 + **첨부 텍스트** + enrichment 를 청크로 만들어 **전부 임베딩**한다 (`chunkWithEnrichment`). 첨부 선별이 없다.

정책에 첨부가 여러 개일 때, 일부는 RAG 검색에 가치가 낮다 (단순 서식·동의서·신청서 양식·반복 boilerplate). 이런 저가치 첨부까지 임베딩하면:
- 벡터 검색에 노이즈가 섞여 Q&A 품질 저하
- 불필요한 임베딩 비용

## 목표

정책에 **첨부가 여러 개일 때, LLM 이 각 첨부의 내용이 RAG 임베딩에 가치 있는지 판단**하여, 가치 있는 첨부만 임베딩한다.

## 범위 결정

- 백엔드 `rag` 모듈 변경. n8n 크롤(몽땅청년 등)과 독립.
- n8n 의 파일명 화이트리스트(`attachments 승격`)는 **1차 필터로 유지**. 본 게이트는 **2차 정밀 선별**(내용 기반).
- 첨부 0~1개면 LLM 생략(그대로 포함). **2개 이상일 때만** LLM 판단.

## 접근

### 위치
RAG 인덱싱 파이프라인에서 **청킹/임베딩 전**에 첨부 선별 게이트를 둔다. 첨부의 추출 텍스트(`policy_attachment.extracted_text`)가 준비된 시점에서, 임베딩 대상에 포함할 첨부를 LLM 이 결정한다.

### 판단 근거
- **추출된 텍스트 내용 기반** (파일명만으론 부정확 — "붙임1.hwp" 등 무의미한 이름 많음).
- 입력: 정책 맥락(제목/요약) + 각 첨부의 내용(긴 경우 앞부분 N자 또는 경량 요약).
- 출력: 첨부별 `{ embed: true/false, reason }`.
- 기준 예시: 실질 정책내용(대상·금액·일정·절차) = 포함 / 단순 서식·동의서·개인정보동의·반복 안내문 = 제외.

### 비용 방어 (컨벤션 준수)
- **캐시**: 첨부 내용 hash 키로 판단 결과 캐시 → 변경 없으면 재판단 안 함 (`metrics`/변경감지 패턴 재사용).
- **변경 감지**: 첨부 텍스트가 바뀐 경우만 재판단.
- 첨부 1개 이하면 LLM 미호출.
- 모델: 경량 모델(`gpt-4o-mini` 등)로 판단.
- 비로그인 핫패스 비유발: 본 게이트는 인덱싱(백엔드 비동기 이벤트) 단계라 사용자 요청 핫패스와 무관.

### 결정 저장
- 첨부별 임베딩 포함 여부를 영속화 (예: `policy_attachment` 에 `embedding_included`(bool) + `embedding_decision_reason`(text) 또는 별도 판단 캐시 테이블).
- 어드민에서 검토 가능하도록 노출 고려(선택, 별도).

## 데이터 흐름

```
정책 인덱싱 트리거 (PolicyUpsertedEvent → RagIndexingService)
  → 첨부 N개 로드 (extracted_text)
  → [N>=2] LLM 첨부 선별 게이트 (캐시 확인 → 미스만 LLM 호출)
       → 각 첨부 embed: true/false 결정·저장
  → 포함 결정된 첨부만 청킹 대상으로
  → 본문 + 선별첨부 + enrichment 청킹 → 임베딩 → 저장
```

## 에러 처리

- LLM 실패/타임아웃 → **fail-open**(해당 첨부 포함)으로 폴백하여 콘텐츠 손실 방지. 경고 로그.
- 캐시 조회 실패 → 재판단(또는 포함)으로 폴백.

## 테스트

- 단위: 첨부 2개 이상 시 게이트가 호출되고, mock LLM 응답대로 선별되는지.
- 단위: 첨부 1개 이하 시 LLM 미호출(그대로 포함).
- 단위: 캐시 히트 시 LLM 미호출.
- 통합: 저가치 첨부가 임베딩(`policy_document`)에서 제외되는지, 고가치는 포함되는지.

## 미해결 / 구현 시 확정할 점

- **정확한 통합 지점**: 첨부 텍스트가 인덱싱 `content` 에 합쳐지는 시점이 ingestion 인지 indexing 인지 확인 후, 게이트 위치 확정 (`RagIndexingService` vs 상위 assembling 단계).
- 긴 첨부의 판단 입력(전체 텍스트 vs 앞부분 N자 vs 요약) — 토큰 비용 균형.
- 판단 결과 저장 위치(`policy_attachment` 컬럼 vs 별도 캐시).
- 임계 기준(포함/제외)의 프롬프트 기준선 — 초기엔 보수적으로(애매하면 포함).
- 어드민 노출 여부(검토 UI) — 본 spec 범위 밖일 수 있음.
